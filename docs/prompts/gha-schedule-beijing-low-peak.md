# 提示词：把 GitHub Actions 定时任务调整到北京低峰期

> 适用场景：任何项目需要把每日/定时 GitHub Actions 任务（schedule cron）放到北京时间的低峰期运行。
> 直接复制给任意 AI 助手即可。

---

## 任务

我的项目有 GitHub Actions 定时任务，当前运行时段不是北京低峰期，请帮我调整到合适时间并更新到远端。

## 步骤

1. **先报当前时间**：分别输出本机时间、UTC 时间、北京时间（UTC+8 = 本机 +8 小时），用 `date` 命令实测核对。
2. **找到所有定时配置**：搜索仓库中全部 schedule/cron 配置（通常在 `.github/workflows/*.yml`），逐个列出：cron 表达式 → UTC 时间 → 对应北京时间。
3. **核实 GitHub Actions schedule 限制**（用 web 搜索最新资料确认）：
   - cron 一律按 **UTC** 解释，不是本地时区（最常见踩坑点）
   - 最短触发间隔为每 5 分钟一次
   - **不保证准时**：流量高峰时 schedule 事件可能延迟数分钟到数十分钟，有实测 39 分钟延迟案例
   - 公开仓库不限 Actions 分钟数；cron 没有"某时段禁止运行"的限制
4. **评估任务耗时**：如果管线耗时较长（如抓取 + LLM 处理 + 构建，可能 1-2 小时），目标开始时间要提前，确保数据在用户早晨使用（建议 07:00 前）之前就绪。
5. **给出建议时间**：
   - 北京低峰期通常取凌晨 02:00–05:00
   - 换算公式：`cron(UTC) = 北京时间 − 8 小时`（结果 < 00:00 时日期减一天，cron 只写时刻）
   - 例：北京 04:00 → UTC 前一日 20:00 → cron `0 20 * * *`
   - 权衡说明：北京凌晨 = 美国白天 = Actions 可能较忙；若对延迟敏感可往 UTC 22:00（北京 06:00）方向折中，但会贴近早晨
6. **修改工作流文件**：更新 `schedule.cron`，在注释中写明"北京时间 = UTC 前一日 HH:MM"的换算，并说明选择理由。
7. **同步文档**：更新所有提及运行时间的文档（README、AGENTS.md、CLAUDE.md 等），避免描述与实际 cron 漂移。
8. **验证并推送**：校验 YAML 语法 → commit（消息写明新旧 cron 与北京时间对应）→ push → 确认远端已同步（`git status -sb` 无 ahead）。

## 输出要求

- 时间换算表：`cron 表达式 | UTC | 北京时间`，每个被修改的任务一行
- 修改的文件清单
- 推送结果确认（远端 commit hash）
